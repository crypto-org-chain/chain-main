# v9 upgrade notes

The `v9` upgrade moves chain-main from Cosmos SDK v0.53 to v0.55.1, CometBFT v0.38 to v0.40.0, and ibc-go v10 to v11.2.1-rc.2.

## Before the upgrade

- **Switch binaries at the upgrade height.** A v8 node and a v9 node cannot agree on the same block. All validators must run v9 from the upgrade height on.
- **Move funds out of group policy accounts.** `x/group` is removed. A group policy account can only act through a group proposal, so funds left in one cannot be moved after the upgrade.
- **Keep `data/upgrade-info.json`.** The v8 node writes it when it halts at the upgrade height. A node with memiavl enabled reads it to drop the `group` store and cannot start at that height without it. Copy it along if you move the data directory.
- **Stop using `chain-maind rosetta`.** The command is removed.
- **Remove `--trace-store` from start scripts.** The flag no longer exists.

## Building

- Go 1.26.11.
- RocksDB 10.9.1 for RocksDB builds. The Nix build already pins it.

## What the upgrade does

The handler runs once at the upgrade height.

| Module | Version | Change |
| --- | --- | --- |
| `auth` | 5 → 7 | Removes the account number counter. Adds the `sig_verify_cost_mldsa65` param. |
| `staking` | 5 → 6 | Adds the `key_rotation_fee` param, set to `1000000` of the bond denom. |
| `mint` | 2 → 3 | Adds the `max_supply` param, set to `0`. |
| `feegrant` | 2 → 3 | Repairs expiry queue entries that were stored with an empty value. |

It also:

- Drops the `group` store on nodes with memiavl enabled. Other nodes stop loading it and keep its data on disk.
- Converts any account at the `key_rotation_fee_pool` address into a module account with the burner permission. A vesting account there loses its vesting schedule.
- Rebuilds the staking index of pending unbonding delegations, redelegations, and unbonding validators, so the ones started before the upgrade still complete.

## New features

### Validator consensus key rotation

A validator operator can replace the consensus key without unbonding:

```bash
chain-maind tx staking rotate-cons-pub-key --help
```

- Each rotation burns the `key_rotation_fee`. On mainnet that is `1000000basecro` (0.01 CRO). Governance can change it.
- A validator can rotate once per unbonding period.
- The new key takes effect two blocks after the transaction.
- Only key types listed in `consensus_params.validator.pub_key_types` are accepted.

Indexers and monitoring that key validators by consensus address must handle the address changing. The `rotate_cons_pubkey` event is emitted when a rotation is scheduled, and `apply_cons_pubkey_rotation` when it is applied.

### ML-DSA-65 validator keys stay disabled

The upgrade does not change `consensus_params.validator.pub_key_types`. Validators keep using ed25519 keys.

Enabling ML-DSA-65 later takes a governance proposal that adds `ml_dsa_65` to that list. Do not pass one until every IBC counterparty can verify ML-DSA-65 signatures. A counterparty that cannot will stop accepting chain-main headers, and IBC packets to it will stall.

### ML-DSA-65 account keys

Accounts can use ML-DSA-65 keys:

```bash
chain-maind keys add <name> --algo ml_dsa_65
```

Signature verification gas for these keys is set by the `sig_verify_cost_mldsa65` auth param. Existing accounts are not affected.

## IBC

- chain-main can verify headers from counterparty chains whose validators use ML-DSA-65 keys. Existing clients need no change.
- `MsgSubmitMisbehaviour` is removed. Submit misbehaviour with `MsgUpdateClient`.
- **Relayers:** a client update for an ML-DSA-65 counterparty is about 7.4 KB per validator. That is 737 KB for 100 validators. Check that `mempool.max_tx_bytes` on the nodes you submit to is large enough.

## Node operators

- `broadcast_tx_*` RPC endpoints return an error while the node is block syncing or state syncing.
- New `config.toml` files default `mempool.max_tx_bytes` to 4 MB instead of 1 MB. Existing files keep their value.
- The gRPC `max-send-msg-size` default drops from about 2 GB to 10 MB. An `app.toml` that sets the key keeps its value. Set it higher if a node serves larger query responses.

## Indexers and dapps

- The `x/group` messages, queries, and events are gone.
- New accounts no longer get the next sequential account number. The number is derived from a hash and is always 2^63 or larger. Parse it as an unsigned 64-bit integer, not a signed integer or a JavaScript number. Existing accounts keep their numbers.
- The `proposal_messages` attribute of `x/gov` events no longer starts with a comma.
- CLI query output names `Any` values by type URL instead of amino name. `chain-maind query auth account` prints `/cosmos.vesting.v1beta1.DelayedVestingAccount`, not `cosmos-sdk/DelayedVestingAccount`. REST, gRPC, and sign bytes are unchanged.
- `x/authz` removes at most 200 expired grants per block, so a large batch is cleaned up over several blocks.
- The `x/feegrant` `Allowances` and `AllowancesByGranter` queries now apply `offset` and `count_total` correctly.
- `MsgUndelegate` and `MsgBeginRedelegate` use more gas while many unbondings are pending: about 264 gas for each distinct pending completion time. A queue gains at most one completion time per block, and each stays for the unbonding period. Simulate the gas instead of using a fixed limit.
- When a reward payout in the begin or end blocker targets a blocked address, it goes to the delegator or validator owner, then to the community pool, instead of failing.
